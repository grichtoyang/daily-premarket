## 1. 目標與驗收原則

目標：以 Master 既有分析文字品質作為最低保留基準，在不退化的前提下逐區塊改善，追求至少 95% 接近專業 AI 逐區塊解讀。不得因追求新架構而推倒 Master 已有分析邏輯；95% 是品質目標，未逐區塊評分前不得宣稱達標。

每個區塊分析須做到：
1. 數據解讀：引用該區塊實際有效數據、單位、日期與資料來源。
2. 關係分析：解釋指標之間的支持、背離、抵銷或存量／流量差異。
3. 市場判斷：從證據推導有限度結論，不將單一指標誇大為整體方向。
4. 風險與反證：指出什麼條件會推翻目前判斷；資料不足時明確降級。
5. 操作意義：提出可觀察的確認條件、失效條件或等待條件，不得把分析寫成無條件買賣指令。

禁止：
- 只重述數字或只換句話說。
- 跨區塊共用無關的固定敘述。
- 無數據支持的因果推論、方向預測、機率或勝率。
- 把缺值當 0、中性或有利訊號。
- 將 Bias 分數直接當成分析結論。
- 編造資料來源、日期、樣本、關鍵價位或市場事件。

## 2. 17F 與 AI 的責任分工

### 17F 量化層
保留 17F，負責可重現的因子計算：原始值、方向化分數、Base／Adaptive／Effective Weight、因子貢獻、有效覆蓋率、缺值與信心等級。17F 不負責撰寫自然語言分析，也不得單獨代表市場全貌。

### AI 分析層
逐區塊讀取結構化資料與 17F 結果，執行該區塊專屬的交叉分析、判斷、反證與操作觀察。AI 不得改寫原始數字、重算或覆蓋 17F 權重，也不得填補缺失資料。

### 程式驗證層
負責 schema、數字／單位／日期引用、缺值、輸出長度、禁用空泛句、來源追溯及 JSON 格式驗證。AI 輸出不通過時不得靜默當成成功分析。

## 3. 執行架構

1. Builder 產生標準化的區塊 context：區塊 ID、名稱、頁籤、原始欄位、數值與單位、來源日期、資料品質、相關 17F 因子及可用歷史序列。
2. 每個區塊使用獨立的 analysis profile，定義必須回答的問題、可交叉比對欄位、禁止推論與操作觀察條件。
3. LLM 依 profile 產生結構化結果（evidence / relationships / interpretation / invalidation / action_watch / limitations）。
4. 程式驗證結果後，映射回既有 Dashboard 卡片欄位；保留現有 UI schema，避免重做圖表與版面。
5. LLM provider 必須可替換，API key 只由 GitHub Actions Secrets 注入，不得寫入 repo、JSON、log 或 HTML。
6. LLM 不可用、逾時、輸出無效或驗證失敗時，明確標記 fallback／analysis_status，不得把固定句型包裝成 AI 成功結果。fallback 只能輸出精簡、可驗證的資料摘要與限制聲明。

## 4. 區塊分析 profile 分群

各區塊仍須有獨立 ID 與 profile；分群只共用底層計算工具，不共用同一段分析文字。

- 市場總覽／廣度：指數漲跌、漲跌家數、成交金額、漲跌停與市場廣度。
- 法人與三市場籌碼：現貨法人、期貨淨 OI、日夜盤淨交易、選擇權法人流量；明確區分存量與流量。
- 期貨結構：日夜盤價格、基差、成交量、法人 OI、前十大多空與分歧。
- 選擇權結構：PCR、Call／Put OI、Wall、Gamma Wall、Flip、Max Pain、GEX、IV Skew、期限結構。
- 國際市場：美股／亞洲指數、美股期貨、美債殖利率、匯率、商品、ADR、VIX、DXY。
- 技術與相關性：RSI、MACD、KD、均線、歷史相關矩陣；相關性必須日期對齊且樣本充足。
- 情境與執行：Bias、17F 因子、多空條件、三劇本、關鍵水位、交易計畫；必須提供觸發／失效條件，沒有經驗證的模型不得產生機率。

## 5. 品質驗收（每個可見區塊逐一評分）

| 維度 | 分數 |
|---|---:|
| 數據正確、單位／日期／來源可追溯 | 20 |
| 指標交叉關係與背離分析 | 25 |
| 市場解讀與推理品質 | 25 |
| 風險、反證及資料限制 | 15 |
| 操作觀察條件具體且不越權 | 15 |
| 合計 | 100 |

- 每個適用區塊目標 >=95/100；不適用的維度須說明，不可任意灌分。
- 數據正確性為硬門檻：任何虛構數字、錯誤單位、錯誤日期、錯誤引用即 FAIL，不論總分。
- 必須用真實 DATA_REPORT 產生樣本，逐區塊人工檢查；至少涵蓋資料充足、部分缺值、關鍵訊號互相矛盾三種情境。
- 只有單一模型時，Auditor 屬自我複核，不得宣稱獨立多模型審核。
- 未經逐區塊評分與實際 Dashboard 驗收，不得宣稱 95% 達標。

## 7. Master 與工作分支的分析品質差異（2026-11-02）

- 已直接比較 Master 與工作分支的 `build_41_cards()`。Master 版本雖有部分硬編碼門檻／假設需清理，但有較多具體情境解讀，例如法人三市場分歧、前十大與外資部位對照、三劇本條件、17F 因子解讀等。
- 工作分支在資料缺值保護、OI 存量與日夜盤流量區分、選擇權日夜盤拆分等方面增加了保護，但同時把多處分析文字改成中性摘要或限制聲明，且 KPI／開盤前必核／AI 5 面向仍共用相同內容。結果是避免部分錯誤推論，卻明顯降低了分析深度。
- 正確方向不是整套推倒重寫或立即強制導入 LLM，而是以 Master 的分析深度為基準，保留工作分支的資料真實性／缺值防護，再逐區塊修正其硬編碼與錯誤推論。

- `scripts/v9_pro_builder.py` 的 `build_41_cards()` 目前建立分析卡片。
- 不同卡片存在共用文字，例如「KPI 8宮格」、「開盤前必核」、「AI 5面向」共用同一組 look／compass／target；部分期貨／選擇權卡亦共用 futures／options 摘要。
- `V9Analyzer` 已有 17F 因子分數、權重、貢獻及資料覆蓋資訊；應保留作為量化輸入，不應拿來代替區塊推理。
- 目前 `.github/workflows/daily-premarket-v9-pro.yml` 未發現 LLM provider API secret 注入或模型呼叫設定。這只代表尚未具備可確認的 Actions LLM 執行條件，不代表必須先導入 LLM 才能改善品質；先修復既有分析邏輯。
- 目前資料輸出 schema 有既有 `analysis.cards`，優先相容現有 UI，不先重做前端。
