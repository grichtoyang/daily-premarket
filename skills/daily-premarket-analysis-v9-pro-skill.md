## 3. 目前可確認的執行流程

V9 Pro GitHub Actions Workflow 的可見流程如下：

1. 由排程、符合路徑的 Push，或 workflow_dispatch 觸發。
2. 解析指定日期或選取最新的 `DATA_REPORT_YYYYMMDD.md`。
3. 執行 `scripts/v9_pro_builder.py`，產生 `dashboards/data-YYYYMMDD.json`。
4. 驗證 JSON 可解析。
5. 讀取 `templates/v9-pro-react-template.html`。
6. Workflow 將資料 JSON 注入 HTML 的 `window.DASHBOARD_DATA`，並套用 React 資料綁定修正。
7. 產生 `dashboards/v9-pro-YYYYMMDD.html`。
8. 更新 `data-latest.json`、`v9-pro-latest.html`、`index.html` 與 `manifest.json`。
9. 將 `dashboards/` 上傳為 GitHub Pages artifact，部署至 GitHub Pages。

注意：Builder 的實際輸出、母版的資料讀取方式及 Workflow 的注入步驟，必須以三個檔案當前版本交叉核對。不可沿用舊文件中「正式環境 fetch JSON、Builder 只產 JSON、不產 HTML」等未必符合現行 Workflow 的敘述。

## 4. 執行方式

依目前 Workflow 使用的參數格式執行：

```bash
python scripts/v9_pro_builder.py \
  --data_report data_reports/DATA_REPORT_YYYYMMDD.md \
  --out dashboards/data-YYYYMMDD.json \
  --date YYYYMMDD
```

實際執行前先確認輸入報告存在、日期正確及輸出路徑正確。不得以舊日期範例或 Skill 中的歷史測試數字代替當日資料。

## 6. 分析資料與可信度規則

### 6.1 17F 與技術指標

舊版規格曾描述 15 個基礎因子加 RSI、MACD 為 17F，並提及 VIX 動態權重、RSI/MACD 備援與 SQLite 歷史資料。這些描述不等同於每一項功能目前都已正確實作。

每次修改分析引擎時，必須逐項核對：
- 因子清單、輸入欄位及資料來源。
- 基礎權重採相對權重點數（目前總和 104），不是百分比；動態調整後只對有效因子重新正規化至 100%。缺值因子有效權重為 0。輸出須明確標示 `base_weight_total`、`base_weight_unit=relative_points` 與 `weight_normalization=active_factors_rescaled_to_100_percent`。
- 權重總和、動態權重調整公式及缺值處理。
- RSI、MACD 的資料期間、計算方式及備援來源。
- 缺值時是否停用因子、重新正規化權重，或採取其他策略。
- SQLite schema、歷史資料筆數及回測計算是否真實可用。

不得只根據頁面標示「17F」或 Builder 註解宣稱 17 個因子完整有效。若尚未逐項測試，應標示 NOT TESTED。

### 6.2 真實值、推算值與缺失值

所有重要數據應盡可能保留來源、資料日期、擷取時間及計算方法。呈現時須區分：
- 來源直接提供的真實數據。
- 由來源數據計算出的衍生數據。
- 代理指標或估算值。
- 缺失、過期或無法驗證的數據。

Gamma、GEX、IV、相關性、歷史勝率等項目，只有在資料來源與計算方式可驗證時才能標示為實際計算結果。不可將 fallback、placeholder、預設矩陣或硬編碼值包裝成即時真實數據。

### 6.3 歷史統計

SQLite 檔案存在不代表歷史樣本充足。使用歷史相似度、因子績效或勝率前，必須檢查資料表、日期範圍、有效樣本數、標籤定義及計算程式。樣本不足時明確顯示不足，不得推論為可靠勝率。

## 9. 開發與驗收流程

複雜修改採 Supervisor / Worker / Auditor 工作流程；若實際只有單一模型，必須稱為自我審查，不得宣稱獨立多模型審核。

每次任務至少完成：
1. 需求與影響檔案確認。
2. 修改前檢查及備份／Git diff。
3. Worker 實作並回報修改檔案。
4. 執行適用的語法、資料、建置及 UI 測試。
5. Auditor 對照需求、程式與測試證據。
6. 缺陷修正後重新驗收。

狀態只能使用：
- PASS：有可檢查證據通過。
- FAIL：測試或需求不符合。
- BLOCKED：受外部條件阻擋。
- NOT TESTED：尚未測試。

## 10. Dashboard 數字單位與圖表版面驗收（強制）

修改 Dashboard、Builder、DATA_REPORT 或分析模板前，必須先讀取 `docs/DASHBOARD_UNIT_STANDARD.md`。該文件是 V9 Pro 單位顯示標準。

### 10.1 三層單位契約
- 每個數值欄位必須確認來源單位、Builder 標準單位、Dashboard 顯示單位。
- 不得依數字大小推測單位；來源定義不明確時標 BLOCKED。
- 任何單位轉換必須寫出公式並以測試驗證倍率、正負值及缺值。
- DATA_REPORT 解析器不可只擷取數字而忽略單位字串；來源單位驗證未完成不得標 PASS。

### 10.2 呈現規則
- KPI、表格、一般分析文字：數字旁須有單位；若表頭已明確定義單位，欄內可不重複。
- 圖表優先在軸標題、圖例或數列名稱標示單位。
- 若每個圖內數值都加單位會造成擠壓、裁切、遮擋或可讀性下降，允許省略逐筆單位，改在圖表緊鄰上方或下方加清楚備註，例如「單位：口」或「價位單位：點」。
- 混合單位圖表必須逐數列標示單位；不可用單一備註涵蓋不同量綱。
- 圖表縮放須標示原始數值、轉換倍率及方向；不可只寫 x10。
- 不得為了塞入單位而造成文字、圖例、數值標籤或圖示重疊。

### 10.3 驗收
- 42 個可見 Dashboard 區塊逐一對照資料欄位、來源單位、Builder 單位及顯示單位；整組 KPI 群依使用者定義計為一個區塊。
- 六個頁籤均須檢查：總覽、現貨、重要市場、期貨、選擇權、綜合分析。
- 桌面與手機實際渲染均須檢查換行、裁切、圖例、數值標籤及文字／圖示重疊。
- 靜態程式檢查不等於實際渲染 PASS。未實際渲染一律 NOT TESTED。
- GEX 的公式、Worker 回傳 schema 與量綱未核實前，單位狀態維持 BLOCKED。
- 驗收結果必須逐項使用 PASS、FAIL、BLOCKED、NOT TESTED；不得把未測試寫成通過。

## 15. 期貨分頁分析文字：易懂、可判斷、可操作且保留深度

期貨頁的分析敘述不能只重複數字或貼上「偏多／偏空」標籤。每個區塊應盡可能回答：
1. **目前看到什麼**：列出資料、比較基準及時間範圍。
2. **這代表什麼**：用白話解釋術語及數字方向，同時保留專業定義。
3. **怎麼判斷**：指出支持訊號、反向訊號及尚未確認的部分。
4. **接下來看什麼**：提供下一個可觀察的價格、流量或部位變化。
5. **何時不成立**：說明條件失效、資料不足或不可追價的情況。

### 15.1 比較基準不得混用
- K 棒實體比較開盤與收盤；表格漲跌比較前結算；跨盤變化比較夜盤收盤與日盤收盤。必須明確說明基準不同，不可把不同口徑數字視為矛盾或直接互換。
- 基差比較同一時點的期貨與現貨價格；正價差表示期貨高於現貨，逆價差表示期貨低於現貨。基差不是指數漲跌預測，也不能單獨作為進場依據。
- 夜盤相對日盤變化是兩個時段收盤價差，不等於夜盤自身漲跌幅，也不保證次日日盤開盤方向。
- 夜盤收盤等於日盤收盤時，次日操作文字應保持中性，不能寫成「守在日盤收盤之上」；須等待有效站上或跌破後再判斷。

### 15.2 OI 是帶方向的持倉存量
- OI（未平倉量）表示尚未平倉的合約部位；必須與日／夜盤淨交易流量分開。
- 若顯示的是帶正負號的淨部位，數值往正方向移動代表淨部位往多方移動，可能是淨多擴大或淨空縮小；往負方向移動代表淨部位往空方移動，可能是淨空擴大或淨多縮小。
- 不可只用「數字變大／變小」判斷部位擴大或縮小；必須同時比較正負號與變化量。
- 前十大與三大法人若屬不同統計群體，必須分開呈現，不得任意相加。

### 15.3 外資流量必須與價格方向交叉判讀
- 價格上升且外資淨買超：方向一致，但仍須等待價格守穩及後續流量延續。
- 價格下降且外資淨賣超：方向一致，但仍須等待價格確認及後續流量延續。
- 價格上升但外資淨賣超，或價格下降但外資淨買超：方向背離；不得追價，等待價格與流量重新確認。
- 流量為零、資料缺值或價格資料不足時，明確降級為中性／待確認；不得用缺值補零或推定方向。
- OI 是持倉存量，日／夜盤淨交易是時段流量，兩者不可相加、相減或互相替代。

### 15.4 劇本與操作建議
- 交易情境至少包含：觸發條件、確認條件、失效條件。
- 「觸及」不等於「有效突破」；必須說明突破／跌破後是否守穩、回測或反抽失敗。
- 方向一致僅代表初步呼應，不代表趨勢已確認或具有已知勝率。
- 不得虛構停損點數、回測勝率或保證性預測；未經回測的條件式劇本必須明確標示非回測機率。
- 資料不足時應說明缺少哪項資料，以及補齊前無法做出哪一種判斷。

### 15.5 驗收要求
- Browser Audit 除檢查術語、基準、單位與三步驟劇本外，亦須檢查當日實際渲染的流量判讀分支與 OI 正負方向解釋。
- 合成案例測試應至少覆蓋：價格上漲／外資淨賣超、價格下跌／外資淨買超、價格與流量同向、夜盤流量為零、流量缺值及 OI 缺值。
- 合成案例通過不代表真實市場分析已驗證；Browser Audit 通過不代表手機畫面人工驗收完成。
- 資料層凍結期間，只能使用 Dashboard 已有資料欄位改善分析文字與呈現，不得為了補強敘事而新增資料擷取、計算欄位或修改資料層流程。
- 若完整 Dashboard Build workflow 會執行資料層測試或 Builder，且本輪只授權 UI 工作，應使用 `.github/workflows/v9-pro-ui-only-audit.yml`：只讀取既有 Dashboard JSON、注入 Template 並執行 HTML／Browser Audit；不可把它描述成資料層驗證或正式 Pages Deploy。


## 16. 全 Dashboard 分析區塊統一文字分析標準（2026-11-11 起適用）

### 16.1 每個區塊固定採三層完整判讀

每個分析區塊均須依序包含以下三層，三者必須形成前後連貫的判讀邏輯，而非重複同一組數字：

1. **分析（發生什麼事？數據代表什麼？）**
   - 說明當前觀察到的數據、比較基準、時間區間及單位。
   - 解釋數據的實際含義及其代表的市場現象。
   - 專業術語第一次出現時，須以一般使用者能理解的白話解釋；例如基差、未平倉量（OI）、相對日盤、淨交易流量、Gamma Wall 等。
   - 不可只把圖表數字換句話說；應說明數字為何重要、反映哪一種市場行為。

2. **判斷（交叉驗證後，代表什麼市場狀態？）**
   - 至少結合該區塊可取得且相關的其他證據，例如價格、成交量、基差、法人部位、日夜盤變化、選擇權口數／金額代理值、技術指標或市場關係。
   - 明確指出哪些訊號互相支持、哪些訊號背離，以及背離對結論的限制。
   - 嚴格區分「觀察到的現象」與「推論出的市場結論」；上漲不等於多方趨勢，下跌不等於空方趨勢，單一法人流量或單一指標也不能直接證明趨勢。
   - 若只有單一有效證據，必須說明判斷信心有限，不可包裝成多項交叉驗證。

3. **操作（接下來觀察什麼？何時能做、何時不能做？）**
   - 提供可執行的下一步觀察重點，盡可能指出明確價位、資料指標或市場條件。
   - 任何方向性操作建議都必須交代三個條件：**觸發條件、確認條件、失效條件**。
   - 說明何種情況應等待、避免追價、降低判讀權重或放棄該劇本。
   - 若該區塊本質上只提供背景資訊，沒有足夠依據形成交易訊號，操作層應明確寫「目前僅供觀察，尚未構成進場條件」，不可為了湊齊三層而虛構交易建議。

### 16.2 五項強制改善原則

1. **白話解釋專業名詞**
   - 每個專業術語在該分頁首次出現時，須用簡短白話說明；後續可使用簡稱，但不可假設一般使用者已理解。
   - 例如：「基差」是期貨價格減去現貨指數的價差；「未平倉量（OI）」是尚未結束的合約部位存量；「相對日盤」是夜盤收盤價與日盤收盤價的差異，不是夜盤自身漲跌幅。
   - 白話解釋不得犧牲專業精確度；若不同商品或欄位的定義不同，應依實際口徑說明。

2. **數據交叉驗證**
   - 不可只根據日盤或夜盤漲跌直接下結論；應結合可用的價格、成交量、基差、法人部位／流量及相關指標。
   - 必須遵守各欄位的統計口徑與時間範圍，不可把不同法人群、不同時段、存量與流量或不同單位混在一起。
   - 沒有可用的第二項證據時，明確標示「尚無足夠交叉證據」，不可聲稱已完成交叉驗證。

3. **區分市場現象與市場結論**
   - 價格上漲、下跌、量增、量縮、法人買賣超、OI 增減等都是觀察到的現象；是否構成多方／空方趨勢、籌碼共識或有效突破，必須由多項證據及價格確認條件支持。
   - 必須同時交代反向證據或尚未成立的條件，避免只挑選支持既有 Bias 的資料。
   - 不得將短線反彈、單一時段變化或單一指標訊號直接升級為趨勢結論。

4. **提供明確交易條件**
   - 價位或指標只作為觀察參考時，須明確標示「觀察位」或「參考位」，不可寫成已成立的支撐、壓力或進場訊號。
   - 觸發條件說明「發生什麼事才開始留意」；確認條件說明「還需要什麼證據才可採取行動」；失效條件說明「發生什麼事就取消原先劇本」。
   - 突破／跌破須區分觸及與有效成立，必要時加入收盤、守穩、回測或反抽確認。
   - 若資料不足以提供可靠價位或停損距離，必須明確說明限制，不可自行補造數字。

5. **說明不確定性與資料限制**
   - 數據缺值、過期、樣本不足、統計口徑不一致或訊號互相矛盾時，必須明確指出。
   - 說明目前哪些結論可以成立、哪些仍不能判斷，以及欠缺哪一項證據。
   - 不得把「未觀察到」寫成「不存在」，不得把缺值當成零，也不得把估算值、代理值或未回測劇本描述成確定事實。
   - 結論信心應與證據完整度相稱；資料不足時應降低語氣強度並優先採取等待策略。

### 16.3 判讀深度驗收：以基差區塊為例

不合格的寫法只重述：「日盤基差 +84.36 點，正價差比例 +0.21%。」

合格的解析應依三層說明：
- **分析**：期貨價格比現貨指數高 84.36 點，代表當下期貨相對現貨呈正價差；先交代基差定義、比較時點及單位。
- **判斷**：正價差可反映期貨相對現貨較強，但不能單獨證明期貨將持續上漲；還要檢查現貨是否同步走強、基差是否持續擴大，以及法人流量是否呼應。
- **操作**：若正價差持續擴大且現貨同步走強，可提高期貨相對強勢的判讀權重；若基差收斂、現貨未跟上或法人流量背離，應降低權重，不可只因正價差而追多。實際觸發、確認及失效價位必須依當日有效資料決定，不得沿用本例數字作為未來交易價位。

以上數字僅為說明文字結構的歷史範例，不是目前市場報價或可沿用的交易條件。

### 16.4 六個區塊／各分頁的落地要求

- 六個主要分析區塊均須有分析、判斷、操作三層；同一分頁內不同區塊可依資料特性調整篇幅，但不得缺少必要的判讀層次。
- 同一指標若在多個區塊重複出現，不必重複貼上相同數字；應補充該區塊新增的交叉關係、判讀差異或下一步觀察條件。
- 區塊之間應形成完整的判讀流程：數據觀察 → 跨指標驗證 → 市場狀態 → 價格／事件觸發 → 確認或失效後的應對。
- 分析文字必須與同區塊圖表、表格、實際資料日期及單位一致；不得出現圖表與文字引用不同日期或互相矛盾的數字。
- 文字應讓一般使用者看得懂，同時保留足夠專業深度；避免只堆疊術語、縮寫或沒有操作意義的形容詞。

### 16.5 Auditor 逐區塊驗收清單

每次修改分析文字或新增分析區塊時，逐區塊檢查：

- [ ] 分析層：有沒有說明數據發生什麼事、數據意義、基準、時間及單位？
- [ ] 名詞層：第一次出現的專業名詞是否有白話解釋？
- [ ] 判斷層：是否結合至少兩項可用證據；若無法做到，是否誠實標示證據不足？
- [ ] 反證層：是否指出背離訊號、反向證據及尚未成立的條件？
- [ ] 現象／結論：是否避免把單一漲跌或單一指標直接當成多空趨勢？
- [ ] 操作層：是否指出下一個觀察重點及可辨識的價位／條件？
- [ ] 三條件：方向性操作是否明確列出觸發、確認、失效條件？
- [ ] 不確定性：缺值、樣本不足、估算／代理值及未回測限制是否清楚揭露？
- [ ] 一致性：文字是否與圖表、表格、日期、數值、單位及統計口徑一致？
- [ ] 可理解性：一般使用者是否能讀懂目前狀態、下一步要看什麼，以及何時不應採取行動？

驗收狀態依實際證據標示 PASS／FAIL／BLOCKED／NOT TESTED。靜態文字檢查不等於實際畫面驗收；Browser Audit 通過也不代表市場判讀品質已完成驗證。此規範只約束分析層與呈現層，不授權修改任何 DATA LAYER FROZEN 項目。
