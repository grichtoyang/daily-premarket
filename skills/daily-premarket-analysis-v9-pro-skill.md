## 2. 系統架構與資料流

V9 Pro 採三層產品架構、四份專項 Skill：

\`\`\`
Fetch Workflow
  → DATA_REPORT（資料層產物）
  → Builder／分析資料 JSON
  → React Dashboard Template
  → Build + Deploy Workflow
  → GitHub Pages Dashboard
\`\`\`

- 資料層：擷取與標準化事實資料，產出 DATA_REPORT。
- 分析層：以已存在的資料欄位形成市場解讀、判斷與操作條件。
- 視覺層：把資料與分析呈現在六個分頁。
- 建置／發布層：負責驗證、組裝、產生 HTML、Artifact 與 Pages 發布。

不要把三層產品架構與四份文件分工混為一談。

## 4. 不可違反的共同原則

1. 以目前分支程式、資料與 Workflow 為準；文件與實作不一致時先查證。
2. 修改前確認分支、HEAD、Git 狀態、目標檔案、差異及觸發的 Actions。
3. 嚴格限定使用者授權範圍，不順手重構、不碰已鎖定頁面、不擴大到資料層。
4. 不捏造資料、來源、數字、計算、測試、部署、Agent 委派或完成狀態。
5. 區分真實資料、衍生計算、代理／估算、缺值與過期資料；缺值不可當零。
6. 區分存量與流量、不同法人群、不同時段、不同單位及不同市場口徑。
7. 分析結論強度必須符合證據；單一訊號不能被包裝成趨勢確認或進場訊號。
8. 任何交易方向均需價格觸發、確認及失效條件；未確認前優先觀察，不追價。
9. 不因「還能潤飾」而持續改動；只處理有明確價值的錯誤、可讀性障礙、分析缺口或操作風險。
10. 使用者已驗收的分頁與視覺設計視為受保護範圍。

## 5. 分析文字共同格式

所有分析卡片維持「分析／判斷／操作」三段，但不為了格式而硬湊內容：

- **分析**：交代實際數據、單位、比較基準、時間範圍及其代表的現象。
- **判斷**：交叉檢查支持與反向證據，指出訊號是否一致、資料限制與信心程度。
- **操作**：說明下一個觀察點、觸發條件、確認方式及失效條件；若未形成交易條件，明確寫等待／觀察。

不得只重述圖表，也不得把文字寫成無依據的預測。專有名詞首次出現時提供精簡白話解釋。

## 6. Supervisor／Worker／Auditor 工作流程

複雜任務預設採以下流程：

- Supervisor：拆解需求、定義授權範圍、檔案清單與驗收標準，整合交付。
- Worker：執行限定修改，提供 diff、測試輸出與可核對證據。
- Auditor：逐項對照需求、程式、數據、測試、文件及風險，缺陷退回修正並複驗。

若實際環境只有單一模型，必須明確稱為單一模型自我審查，不得宣稱獨立多模型審核。不得虛構 Worker 或 Auditor 已由獨立 Agent 執行。

狀態只能使用：
- PASS：有對應證據且已通過。
- FAIL：已確認不符合。
- BLOCKED：受外部條件或資料定義阻擋。
- NOT TESTED：尚未執行或證據不足。

## 7. 修改前與交付前檢查

修改前：
- 確認分支為使用者指定工作分支，記錄 HEAD。
- 檢查目標檔案與目前差異；不得覆蓋未提交工作。
- 先讀相應專項 Skill、單位標準與必要程式。
- 檢查 Push／Workflow path filter，確認會觸發哪些 Actions。

交付前：
- 檢查 diff 僅包含授權檔案。
- 執行與修改範圍相符的測試。
- 分別回報程式測試、瀏覽器測試、部署、使用者人工驗收，不得混為一談。
- 提供實際 commit、Actions run、Pages 網址；不存在的證據不得宣稱。
- 未經使用者驗收的畫面標記為 NOT TESTED／PENDING。
